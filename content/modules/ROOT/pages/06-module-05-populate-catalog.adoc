== The Backstage entity model

Before registering entities (like the Parasol Insurance component in the prior module), it's worth understanding how the catalog organises information:

* **Component** -- A software unit (service, library, website) owned by a team
* **API** -- An interface exposed by a component (REST, gRPC, event)
* **System** -- A group of related components that form a product or capability
* **Resource** -- Infrastructure dependencies (databases, queues, clusters)
* **Domain** -- A business area that owns systems

Each entity is defined in a YAML file (commonly named `catalog-info.yaml`) file that typically lives alongside the source code. The team that owns a component is responsible for maintaining its `catalog-info.yaml` -- just like they maintain the code itself. Developer Hub reads these files and builds the catalog graph.

Not every entity needs a hand-crafted YAML file, though. Integrations like the GitLab discovery provider (which you enabled in the previous module) can scan repositories and auto-register any `catalog-info.yaml` files they find. Other providers go further -- the Keycloak provider you configured automatically imports users and groups from your identity provider, and CI/CD integrations can surface pipeline and deployment data without any catalog changes at all.

== Exercise 2: Explore Parasol's catalog entities repository

While Developer Hub is deploying, let's take a look at the catalog entity definitions being imported.

As part of their IDP adoption initiative, Parasol's teams created catalog entity definitions to document their architecture. This wasn't just for human consumption -- it was also part of their AI strategy: structured, machine-readable documentation that AI assistants can query programmatically.

. Refresh the **GitLab** tab on the right, and open the **parasol-entities** repository
+
image::populate-catalog/gitlab-projectslist-entities.png[The `parasol-entities` repository in GitLab,link=self,window=blank,align="center",width=700,title=The `parasol-entities` repository in GitLab]
. Open the https://gitlab-gitlab.{openshift_cluster_ingress_domain}/parasol/parasol-entities/-/blob/main/catalog-index.yaml[`catalog-index.yaml`,window=gitlab] file at the repository root
+
This is the **catalog index** -- a specialized Location entity that references all of Parasol's architecture definitions. Notice the `spec.targets` array: each entry points to a YAML file containing entity definitions.
. Open https://gitlab-gitlab.{openshift_cluster_ingress_domain}/parasol/parasol-entities/-/blob/main/parasol-foundations.yaml[`parasol-foundations.yaml`,window=gitlab] to see how Domains and Systems are defined
+
Notice the TechDocs annotations (`backstage.io/techdocs-ref`) -- these link to documentation for each Domain, including the PCI-DSS compliance information you'll explore later.

. Open one of the component files, such as https://gitlab-gitlab.{openshift_cluster_ingress_domain}/parasol/parasol-entities/-/blob/main/components/parasol-catalog-claims.yaml[`components/parasol-catalog-claims.yaml`,window=gitlab]
+
See how each component specifies its type, lifecycle, owner, system membership, and API dependencies. This metadata is what powers the System Diagrams and relationship graphs you'll explore next.

Developer Hub is now importing the entity definitions you just explored in GitLab.

image::populate-catalog/catalog-populated.png[Developer Hub catalog showing System entities,link=self,window=blank,align="center",width=700,title=The Developer Hub catalog showing System entities]
. Click on the **API Gateway System** to open its details page

. Click the **System Diagram** button (near the top of the page)
+
This diagram visualizes Parasol's software architecture at scale. Each box represents a Component (service), and the lines show API dependencies between them. You're seeing the entity definitions you just imported -- Domains, Systems, Components, APIs, and Resources -- rendered as an interactive graph.
+
Notice how the diagram shows:
+
* **Components** grouped into their parent System
* **API relationships** showing which services talk to each other
* **Resource dependencies** like databases and message queues
+
image::populate-catalog/system-diagram.png[Developer Hub showing the API Gateway system diagram,link=self,window=blank,align="center",width=700,title=Developer Hub showing the API Gateway system diagram]

. Click **View Graph** (at the top right of the diagram)
+
This opens the full relationship graph with additional depth. You can:
+
* **Zoom and pan** to explore the full topology
* **Click nodes** to see entity details
* **Trace dependencies** across multiple levels (e.g., which APIs a component uses, which resources those APIs depend on)
+
This is the catalog's power: it doesn't just list services, it models the relationships between them. When a developer asks "what does the Billing service depend on?", the graph shows the answer immediately.

. Click **Docs** in the left navigation bar, and use the **Filters** to show *All documentation*

. Click on **Billing & Payments** in the documentation index
+
image::populate-catalog/docs-list.png[The TechDocs list in Developer Hub,link=self,window=blank,align="center",width=700,title=The TechDocs list in Developer Hub]

+
You're now viewing domain-level documentation that lives alongside the catalog entities. This includes:
+
* **Architecture decision records (ADRs)** explaining why the Billing system is structured this way
* **PCI-DSS compliance information** documenting how payment data is handled securely
* **Onboarding guides** for developers joining the Billing team
+
Notice that this documentation is discoverable through the same interface developers use to find services and APIs. It's not buried in Confluence or a wiki -- it's registered in the catalog alongside the code.

== Exercise 4: Query the catalog with Lightspeed

You've just explored the catalog visually as a human. Now see how AI agents can query the same catalog programmatically via the Model Context Protocol (MCP).

[NOTE]
====
The overlay you just deployed includes **Lightspeed** -- an AI assistant integrated into Developer Hub. Lightspeed runs as sidecar containers (llama-stack for LLM inference, lightspeed-core for the service layer) with MCP access to the catalog API.

This means Lightspeed can query real catalog data in real-time -- not generic documentation, but your actual Systems, Components, APIs, and TechDocs.
====

. Open the **Developer Hub** tab and look for the floating **Lightspeed** icon in the bottom-right corner

. Click the Lightspeed icon to open the chat interface

. Try asking Lightspeed about the catalog you just explored:
+
* _"How does Parasol handle PCI compliance?"_
  ** Lightspeed uses MCP to query the catalog's TechDocs API
  ** Retrieves the Billing & Payments documentation you saw in Exercise 2
  ** Returns an answer grounded in the actual compliance documentation
+
* _"What components are in the API Gateway System?"_
  ** Lightspeed queries the catalog API for the API Gateway System entity
  ** Lists the actual Components you saw in the System Diagram
+
* _"What does the Claims service depend on?"_
  ** Lightspeed traverses the catalog's relationship graph
  ** Returns the API and Resource dependencies

. Notice how Lightspeed's answers reference **real entities** from your catalog, not generic responses

. Try one of the pre-configured suggested prompts if available in the chat interface

[IMPORTANT]
====
**This is the platform engineering multiplier effect in action**

You built a machine-readable knowledge graph (the catalog). Now:

* **Humans** can explore it visually (System Diagrams, docs, relationship graphs)
* **AI agents** can query it programmatically (MCP provides structured API access)
* **Both** get authoritative, up-to-date answers from the same source of truth

The catalog you just mapped isn't just documentation -- it's **operational intelligence** accessible to both humans and machines.

When a developer asks Lightspeed "How does Parasol handle PCI compliance?", they get the exact same Billing & Payments documentation you saw in Exercise 2 -- retrieved via MCP, not hard-coded responses.

This is why investing in catalog quality pays dividends: better human discovery AND better AI-powered assistance, both grounded in the same authoritative source.
====

== Module summary

Parasol's Internal Developer Platform now has a mapped software architecture and an AI assistant that can query it.

The software catalog is more than a service registry -- it's a **knowledge graph** that models your entire software landscape. Systems, components, APIs, resources, teams, and documentation are all connected in a queryable structure.

**For humans**, this means:

* **Instant discovery** -- find services, APIs, and docs without filing tickets
* **Visual architecture** -- understand system dependencies through diagrams
* **Integrated information** -- CI/CD status, topology, and documentation in one place

**For AI agents**, this means:

* **Programmatic access** via MCP to query catalog entities in real-time
* **Contextual answers** grounded in authoritative, up-to-date documentation
* **Relationship traversal** to answer questions like "what depends on this API?" or "which team owns the Billing service?"

The catalog isn't just documentation -- it's **operational intelligence** accessible to both humans and machines.
